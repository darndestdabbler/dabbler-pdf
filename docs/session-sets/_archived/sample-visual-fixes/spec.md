> **Purpose:** Fix the visual rendering issues discovered during human review of the 10

## Problem Summary

Human visual inspection of all 10 sample PDFs revealed three systematic issues and
two isolated bugs. The most critical issue — background fill color bleeding into
subsequent text — affects 5 of 10 samples and makes text unreadable in several cases.

## Root Cause Analysis

### Issue 1: Fill Color Bleeds into Text (Critical)

**Symptom:** After drawing a filled rectangle (e.g., a table header background or
alternating row color), subsequent text adopts the fill color instead of black. Column
headings in S06 are invisible. Text in S07, S09, and S10 is too light to read.

**Root cause:** `SampleBase.DrawRectFilled()` calls `SetColorFill()` to paint the
rectangle but never resets the fill color afterward. When `DrawText()` is called without
an explicit color parameter (the no-color overload at `SampleBase.cs:67-74`), it uses
whatever fill color is currently active — which is still the background color.

The colored overload (`SampleBase.cs:77-86`) does reset fill color to black at line 85,
but many call sites use the no-color overload.

**Why it's widespread:** The `DrawRectFilled` → `DrawText` (no-color) pattern appears
in S04 (alternating rows), S06 (table headers and row backgrounds), S07 (page headers),
S09 (invoice line items), and S10 (stress test rows).

**Fix strategy:** Wrap fill operations in `SaveState()`/`RestoreState()` so the graphics
state (including fill color) is automatically restored after each fill. This is more robust
than manual resets because it handles all state — fill color, stroke color, line width, etc.
The `SaveState`/`RestoreState` mechanism already exists in `PdfContentByte` (lines 61-78)
and is already used correctly in S05 for dashed borders.

### Issue 2: Text Labels Shifted Up (Moderate)

**Symptom:** Across multiple samples, labels outside of boxes appear shifted up relative
to where they should be. This is most visible in S08 (padding labels) but also affects S04
(color swatch labels) and S02 (box labels). The human described it as "too much bottom
margin, not enough top margin."

**Root cause:** When positioning text inside or adjacent to a rectangle, the Y coordinate
is used directly as the PDF text baseline. But the baseline is not the top of the text —
it's where the bottom of letters like "a" and "o" sit, roughly 70-80% of the way down from
the top of the text's bounding box. Descenders (g, p, y) hang below the baseline.

The result: text that should appear vertically centered in a box or aligned with a box's
top edge instead appears shifted upward by approximately `fontSize * 0.2` to `fontSize * 0.3`
points.

**Fix strategy:** Adjust the Y offset in text positioning helpers so that the visual top of
the text aligns with the intended position. This means subtracting an ascent-based offset
(approximately `fontSize * 0.8` or using `font.GetAscentPoint()` if available) when
converting from "top of text area" coordinates to PDF baseline coordinates.

### Issue 3: Single Long Word Overflow (Low)

**Symptom:** In S02, the word "Supercalifragilisticexpialidocious" in a 1-inch-wide box
overflows the box boundary instead of being broken or truncated.

**Root cause:** `TextLayout.WrapText()` (line 52-67) and `SampleBase.WrapText()` (line
126-142) both handle multi-word wrapping by splitting on spaces, but when a single word
exceeds `maxWidth`, it's added as-is to a line. There is no character-level fallback.

**Fix strategy:** Add character-level breaking as a fallback in `TextLayout.WrapText()`.
When a single word exceeds `maxWidth`, break it at the character boundary that fits within
the available width. This is consistent with the spec from the `api-gap-enhancements`
session set (Session 2, Step 2, point 4: "When a single word exceeds `maxWidth`, include
it as its own line (no character-level breaking needed for v1)"). This is now v2.

### Issue 4: ActualSize Image Positioning (Low)

**Symptom:** In S05, the "ActualSize" image rendering runs up against the right side of
the page instead of being positioned at the element's top-left.

**Root cause:** In `S05_Images.cs` (line 84), the absolute position calculation places
the image at the wrong X coordinate. The image is positioned at the element's X coordinate
without accounting for the element box layout, causing it to appear too far to the right.

**Fix strategy:** Correct the position calculation so the image's left edge aligns with
the element box's left edge.

## Session Plan

### Session 1 of 2: Fix Color State Bleeding

**Addresses:** Issue #1 (fill color bleeds into text)

This is the highest-priority fix because it makes text unreadable in 5 of 10 samples.

#### Step 1: Fix `SampleBase.DrawRectFilled` with SaveState/RestoreState

Modify `SampleBase.DrawRectFilled()` to wrap the fill operation in `SaveState()`/`RestoreState()`:

```csharp
protected static void DrawRectFilled(PdfContentByte cb, double x, double y,
    double width, double height, BaseColor color)
{
    cb.SaveState();
    cb.SetColorFill(color);
    cb.Rectangle(x, PdfY(y + height), width, height);
    cb.Fill();
    cb.RestoreState();
}
```

This ensures the fill color is restored to whatever it was before the call, eliminating
the root cause across all samples that use this helper.

#### Step 2: Audit the no-color `DrawText` overload

Review `SampleBase.DrawText()` (the overload without a `BaseColor` parameter). If there
are any remaining code paths where text color might be polluted from a non-`DrawRectFilled`
source (e.g., direct `SetColorFill` calls in sample code), add a `SetColorFill(BaseColor.Black)`
at the beginning of the no-color overload as a safety net.

#### Step 3: Audit all 10 samples for direct fill color calls

Search all sample files for any direct calls to `SetColorFill()` or `Fill()` that bypass
`DrawRectFilled()`. These are call sites that won't be protected by the Step 1 fix. For each
one found, wrap it in `SaveState()`/`RestoreState()`.

Known locations to check:
- `S04_Colors.cs` — color swatches and background fills
- `S06_TableLayout.cs` — table header and row backgrounds
- `S07_MultiPage.cs` — page header/footer backgrounds
- `S09_InvoiceSample.cs` — invoice header and line items
- `S10_StressTest.cs` — row backgrounds

#### Step 4: Rebuild and run all samples

```bash
dotnet build DabblerPdf.slnx
dotnet run --project DabblerPdf.Samples/DabblerPdf.Samples.csproj
```

Verify all 10 samples generate without errors. Open the affected PDFs (S04, S06, S07,
S09, S10) and confirm text is now rendering in black (or the intended color) rather than
adopting the background fill color.

#### Step 5: Run existing tests

```bash
dotnet test tests/DabblerPdf.Tests/DabblerPdf.Tests.csproj
```

All existing tests must pass. The `SaveState`/`RestoreState` change is purely additive and
should not affect any existing behavior.

**Creates:** No new files
**Touches:** `DabblerPdf.Samples/SampleBase.cs`, potentially `S04_Colors.cs`,
`S06_TableLayout.cs`, `S07_MultiPage.cs`, `S09_InvoiceSample.cs`, `S10_StressTest.cs`

### Session 2 of 2: Text Positioning, Word Breaking, and Image Fix

**Addresses:** Issues #2 (label positioning), #3 (long word wrapping), #4 (ActualSize image)

#### Step 1: Fix text vertical positioning in SampleBase helpers

Investigate the exact baseline offset needed by checking how `PdfY()` converts top-down
coordinates to PDF coordinates, and how text baseline relates to the visual top of text.

Adjust the Y coordinate in `SampleBase.DrawText()` and `SampleBase.DrawLabel()` so that
the `y` parameter represents the visual top of the text, not the baseline. The adjustment
should be approximately `y_baseline = PdfY(y) - fontSize * ascent_ratio`, where
`ascent_ratio` is derived from the font metrics.

Test the adjustment against the specific symptoms:
- S08 labels should align vertically with their boxes
- S04 color swatch labels should have proper spacing below the swatches
- S02 box labels should have balanced top/bottom margins

#### Step 2: Fix text vertical positioning in TextLayout.DrawText

Apply the same baseline adjustment to `TextLayout.DrawText()` in
`src/DabblerPdf/Text/TextLayout.cs`. When `y` is passed in as the top of the text area,
the first line's baseline should be at `y - ascent` (in PDF coordinates), not at `y`.

This affects any sample that uses `TextLayout.DrawText()` directly (e.g., S02 text wrapping
boxes).

#### Step 3: Add character-level word breaking to TextLayout.WrapText

In `src/DabblerPdf/Text/TextLayout.cs`, modify `WrapText()` to handle oversized words:

```csharp
// After determining a word exceeds maxWidth on its own:
// Break the word character by character
var chars = word.ToCharArray();
var fragment = "";
foreach (var c in chars)
{
    var test = fragment + c;
    if (font.GetWidthPoint(test, fontSize) > maxWidth && fragment.Length > 0)
    {
        lines.Add(fragment);
        fragment = c.ToString();
    }
    else
    {
        fragment = test;
    }
}
// fragment contains remaining characters — becomes the new currentLine
```

Also update `SampleBase.WrapText()` with the same logic for consistency, or remove
`SampleBase.WrapText()` if all call sites can use `TextLayout.WrapText()` instead.

#### Step 4: Fix ActualSize image positioning in S05

In `S05_Images.cs`, correct the `SetAbsolutePosition()` call for the ActualSize case so
the image's top-left corner aligns with the element box's top-left corner.

Review the coordinate math:
- The element box top-left in top-down coordinates is `(ex, y)`
- In PDF coordinates (bottom-left origin), the image position needs to be
  `(ex, PdfY(y) - image.ScaledHeight)` — but verify this is actually what's happening
  and whether `ex` is correctly calculated.

#### Step 5: Investigate S03 line/label alignment

Check whether the line-label alignment issue in S03 (Lines and Shapes) is caused by the
same baseline offset issue from Steps 1-2. If so, it should already be fixed. If it's a
separate issue (intentional positioning), leave it as-is.

#### Step 6: Add unit tests for character-level word breaking

Add tests to the existing TextLayout test file:

- A 34-character word ("Supercalifragilisticexpialidocious") at a width that fits ~10
  characters per line should produce ~4 lines
- A word that exactly fits should not be broken
- A single character that exceeds width should still appear on its own line
- Mixed content: normal words plus one oversized word in the middle

- S04: Color swatch labels have proper spacing
- S05: ActualSize image positioned at element top-left, not running off to the right
- S06: Text still rendering correctly (regression check from Session 1)
- S07: Text still rendering correctly (regression check from Session 1)
- S08: Labels properly aligned with their boxes
- S09: Text still rendering correctly (regression check from Session 1)

## Cross-Cutting Concerns

### No Library API Changes

All fixes in Session 1 are in the samples project (`DabblerPdf.Samples`), not the library.
Session 2 modifies `TextLayout.WrapText()` in the library — this is an additive behavior
change (character-level fallback where none existed before). No existing public API
signatures change.

### Backward Compatibility

The `TextLayout.WrapText()` change adds character-level breaking for oversized words. Any
caller that previously received a single long line will now receive multiple shorter lines.
This is a bug fix, not a breaking change — the prior behavior (overflow) was incorrect.

### Test Stability

All 562 existing tests must continue to pass after each session. New tests are added only
for the character-level word breaking (Session 2, Step 6).

### Visual Verification

Each session ends with regenerating all 10 sample PDFs and visually inspecting the affected
ones. The human will do a final visual review after Session 2 to confirm all issues are resolved.
