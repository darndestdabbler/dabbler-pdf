  2. TextLayout.WrapText (src/DabblerPdf/Text/TextLayout.cs) splits each paragraph with Split(' ', StringSplitOptions.RemoveEmptyEntries) and rejoins the words with one space, so every run of spaces becomes a single space even when the text already fits: "New Address Eff: 03/01/2024" comes back as "New Address Eff: 03/01/2024". Change it so that:
  • a paragraph that fits within maxWidth is returned exactly as given, leading, interior and trailing spaces included;
  • a paragraph that does not fit breaks only at a run of spaces; the run at which a break is taken is dropped (no line ends or starts with it), and every other run is kept at its full length;
  • explicit \n breaks, the empty-string result and the character-level break of a word wider than maxWidth behave as they do today.

CountLines, MeasureHeight and DrawText follow, because they call WrapText. Say in the XML doc of WrapText what happens to spaces. In tests/DabblerPdf.Tests/Text/TextLayoutTests.cs add tests for: a double-spaced line that fits is unchanged; "CT 06516" keeps both spaces; a break taken at a double space leaves neither line with a leading or trailing space; a double space elsewhere on a wrapped line survives; DrawText emits the double space in its Tj operand. The step's check: dotnet test DabblerPdf.slnx --filter "FullyQualifiedName~TextLayoutTests" passes, the 21 existing tests unchanged in what they assert.

PdfWriter.FlushCurrentPage and PdfTemplate deflate a content stream only when its uncompressed length is over 128 bytes, so a small page is written as plain operators and the same page with one more line is written with /Filter /FlateDecode; nothing documents this and nothing turns it off. Add a public bool CompressContentStreams property to PdfWriter, default true, read when a page or a template created by that writer is flushed: false writes page and template content streams uncompressed whatever their length. Font programs and images are not affected. In tests/DabblerPdf.Tests/Pdf/PdfWriterTests.cs and PdfTemplateTests.cs add tests for: default settings, a content stream of 128 bytes or fewer has no /Filter and one over 128 bytes has /FlateDecode; with CompressContentStreams = false a page and a template over 128 bytes have no /Filter and their text is found in the file's bytes. In README.md, state the 128-byte rule and the property in the section that describes testing generated PDFs, and say that a byte-level text search needs one or the other. The step's check: dotnet test DabblerPdf.slnx --filter "FullyQualifiedName~PdfWriterTests|FullyQualifiedName~PdfTemplateTests" passes.

TextLayout.WrapText stops collapsing runs of spaces: a paragraph that fits is returned exactly as given, and a paragraph that does not fit breaks only at a run of spaces, dropping only the run where the break is taken and keeping every other run at full length; explicit \n breaks, the empty-string result and character-level breaking of an oversized word are unchanged, and CountLines, MeasureHeight and DrawText follow. Finally, tests pin that a Base 14 WinAnsi font draws Polish and Cyrillic text without throwing, writes each character outside Windows-1252 as '?', and measures it as '?' -- Type1Font.GetCharWidth currently indexes its width table by the raw Unicode code (giving 0 for such characters), so it is changed to measure through the Windows-1252 mapping with '?' as the fallback, and the README's font section states the limit.
